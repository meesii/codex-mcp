# codex-mcp 1.0 治理基线

## 目标

1.0 是一次有意的 breaking release。旧命令、旧配置、旧 OAuth 状态和旧的兼容入口不再作为运行时契约保留。首次升级需要重新执行 `codex-mcp setup`，现有 OAuth 会话全部失效。

治理顺序是：先冻结契约，再清理 CLI/config/runtime 生命周期，随后补齐黑盒验收，并将本机管理面升级为独立 Controller + 完整 Web Console。安全边界和已经验证的底层实现不因“清理历史代码”而删除。

## 1.0 用户命令

```text
codex-mcp setup
codex-mcp start [--local] [--no-tunnel] [--tunnel-logs] [--root DIR]
codex-mcp stop
codex-mcp restart
codex-mcp status [--json]
codex-mcp project list
codex-mcp project add [DIR]
codex-mcp project remove [ID|NAME|DIR]
codex-mcp project info [ID|NAME|DIR]
codex-mcp logs [--follow] [--lines N]
codex-mcp doctor [--fix]
codex-mcp auth
codex-mcp update
codex-mcp help
codex-mcp version
```

`daemon` 和 `controller` 都是内部进程入口，不在帮助和用户契约中出现。裸 `codex-mcp` 只显示帮助；启动必须显式使用 `codex-mcp start`。

## 删除的历史入口

- `tunnel`：公网连接配置统一进入 `setup`。
- `exit`：停止服务使用 `stop`，停用项目使用 `project remove`。
- `serve` 和 `--foreground`：统一为 daemon 管理的 `start`；开发调试使用 `--local`。
- `-f` 的上下文复用：只保留 `logs --follow`。
- 旧的 flat public access 字段：不再从 `config.json` 自动迁移。
- `workspaces`、`permissions`：不再读取、不再静默忽略。
- 旧 OAuth approve/pending flow 和兼容 endpoint：只保留当前 router-native authorize flow。
- 已删除工具的兼容别名和旧 action snapshot：由 ChatGPT 重新扫描 1.0 工具列表。

## 配置与状态

1.0 只接受当前 tagged `publicAccess`、`capabilities`、`clientCapabilities`、`ui` 配置模型。旧配置文件存在时，setup/doctor 必须给出明确的“需要重新 setup”错误或由显式 reset 流程处理，不能把坏配置当成空配置。

`oauth-state.json`、`daemon.json`、`projects.json`、`session-bindings.json` 不做旧版本兼容读取。状态损坏必须报告错误；文件不存在才表示空状态。

持久化文件继续使用 exact schema + `schemaVersion`。daemon HTTP control API 单独使用 `controlApiVersion: 1`：同一协议 major 必填字段严格校验，但允许新增未知字段，以便 1.0.x CLI/daemon 滚动更新；协议版本不匹配才拒绝操作。

## 必须保留的安全边界

- OAuth PKCE、private_key_jwt、resource binding 和 credential generation。
- safe HTTP 的 SSRF、DNS rebinding、redirect、size 和 timeout policy。
- canonical project path、symlink containment 和项目隔离。
- daemon control 的 loopback + random token gate。
- process owner scope、process tree shutdown 和输出预算。
- Tunnel candidate、DNS cutover、公网 probe 和补偿流程。
- private atomic file write 与敏感配置权限。

## 本机 Controller / Web Console 边界

Web Console 是 CLI 的完整本机 GUI 控制面，而不是只读状态页。Controller 独立于 MCP Runtime：`stop` 只关闭 MCP Runtime、Tunnel 和项目运行时，Controller 与网页继续存活，因此可直接从网页再次 `start`。setup/auth/doctor/update/project/logs 等用户级 CLI 能力均有对应 Web 操作。

Controller 只监听 loopback，并与公网 MCP/OAuth listener 分离。浏览器使用随机 HttpOnly、SameSite=Strict session cookie；所有 mutation 还要求同源 Origin + CSRF token。CLI 使用 `controller.json` 中的独立随机 control token，浏览器永远拿不到该 token。页面使用每响应随机 nonce CSP，管理 API 与日志禁止缓存；长任务通过 operation + SSE 暴露阶段、结果和取消。Cloudflare 登录输出会进入 operation，以便自动打开浏览器失败时仍可看到授权地址。


## 生命周期提交点

- 普通 `start` / `project add` 复用已有运行意图；显式模式选项才触发模式切换。切换与 restart 在停止前验证已提交的配置和密码。
- 生命周期锁统一串行化 start、stop、restart、离线项目停用和公网 setup。
- 启动 CLI 持有子进程直到 daemon 完成服务启动、公网 probe 和状态提交。启动超时或信号取消会清理本次子进程；启动期 IPC 断开会取消未提交实例。
- Tunnel 注册最多 180 秒，启动公网 probe 使用一个 30 秒总预算；启动 CLI 最多等待 300 秒，失败后执行有界进程清理。
- 项目注册、绑定和 OAuth 都在私有原子文件提交成功后发布内存状态。OAuth 刷新重放撤销须先提交再返回协议错误。
- 会话 binding 的 `lastSeenAt` 最多每 10 分钟持久化一次；bind/unbind/invalidate 仍立即提交，避免每次项目工具调用都重写整个 bindings 文件。
- 多项目 daemon 不创建启动 cwd 对应的默认 `ProjectContext` / process pool；项目运行时只由显式 conversation binding 懒加载。

## 兼容边界

移除旧 cloudflared 人类可读表格解析、未使用的默认技能发现入口和批量停用入口。第三方当前协议所需的 SDK `legacy: "stateless"` 选项、ChatGPT widget 元数据、OAuth DCR/CIMD 与 Windows 文件替换恢复保留；这些不是旧 codex-mcp 配置迁移。

## 验收依据

- `test/cli-contract.test.js`：构建产物 CLI、旧入口拒绝、状态损坏、项目持久化、Controller 可写 Web Console、CSRF/Host 边界与 Runtime stop 后 Web 重启。
- `test/lifecycle.test.js`：启动超时和父进程断开、Tunnel 退出与有界恢复、日志轮转。
- `test/mcp-tools.test.js`：真实 HTTP 调用固定 15 个工具；文件写入结果、项目/会话/进程/技能/下游 MCP 隔离。
- `test/oauth.test.js`：真实 HTTP OAuth、PKCE、令牌轮换/撤销、凭据 generation、private_key_jwt 和写盘失败恢复。
- `test/security.test.js`：SSRF 与 socket DNS 校验、HTTP 预算、精确 Tunnel probe、路径与 symlink 边界、进程树和输出上限。

本地测试不能证明 ChatGPT 账户中的连接器已启用，也不能代替真实 Cloudflare DNS 切换与跨平台 CI。发布前需在目标平台运行 CI，并通过 ChatGPT 实际调用核对连接器状态。
